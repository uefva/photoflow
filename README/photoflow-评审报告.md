# photoflow 工作流评审报告

评审日期：2026-11-26
评审对象：`photoflow.py`（2016 行，含图形界面）、`photoflow.bat`、`test/` 下三个测试脚本、README 与两份说明文档
评审方式：通读代码 + 实跑测试 + 在临时目录复现边界场景（未触碰真实照片库 J 盘）

---

## 一、总体结论

这套工作流的骨架是成立的，而且设计得相当克制：用「目录是否被相册索引」来做去重，不建数据库、不写 sidecar、不打标记，这个思路和它要解决的问题（NAS 相册时间线里每张照片只出现一次）严丝合缝。代码层面的安全设计也确实下了功夫——跨卷移动是「复制 + 哈希校验 + 删源」而不是信 `shutil.move`，预演指纹能锁住清单，中途失败不留半截文件。这些在临时目录里实测都通过了。

但存在**一个会造成真实故障的严重缺陷**、**两个会让工作流静默偏离预期的中等问题**，以及一批文档与代码不一致、测试跑不起来的小问题。下面按严重度排列，每条都给出复现方式和修复方向。

严重度记号：**P0** 会导致照片从相册消失或工作流失效；**P1** 静默偏离预期、需要人工兜底；**P2** 报错误导、文档失真、可维护性问题。

## 二、问题清单

### P0-1　成品目录里任何带 `-ed` 的文件都会触发归档，包括非图片文件

**现象。** `archive` 判断「这张原图该归档了」的唯一依据是：成品目录里有个文件，剥掉 `-ed` 后能对上原图目录里的某个文件名。它**完全不检查成品文件的扩展名是不是图片**。而 `-ed` 恰好是多个 RAW 编辑器给**伴生文件**命名时常用的分隔符——Lightroom 的 `.xmp`、Adobe Camera Raw 的 `.acr`、DXO 的 `.dop`、Capture One 的 `.cos`、ON1 的 `.on1`。只要这类文件进了成品目录，对应的原图就会被当成「已修」移进归档，于是这张照片**从被索引的原图目录里消失，而成品目录里根本没有它的成品**——照片在相册时间线里彻底不见。

**复现（临时目录实测，已确认）：**

```
05_JPG图/<批次>/DSC0001.JPG          （一张正常原图）
03_缓存-调色ed/<批次>/DSC0001-ed.xmp （一个伴生文件，不是图片）

$ photoflow archive <批次> --root <库> --apply
待归档    1 个
将移动（原图目录 → 归档目录）：
       DSC0001.JPG  13B  [扩展名不同（原图 .JPG / 成品 .xmp）]
完成：归档 1 个，已在归档中 0 个，内容冲突 0 个，失败 0 个。
```

实测用 `.aae` / `.dop` / `.on1` 三种伴生文件各放一张原图，一次归档把三张原图全部移走，原图目录清零。`.aae` 这种更危险：它是手机照片的「编辑记录」而不是编辑结果，从 iOS 照片或某些导入工具导出时很常见。

**为什么之前的测试没抓到。** 现有测试只覆盖了「成品是图片」的情况，没有一条用例把非图片文件放进成品目录。而工作流说明第五节表格里「`DSC07287-edited.JPG` 不认」这条规则，防的是「误伤本来就叫这个名字的原图」，恰恰没防「非图片文件冒充成品」这个反方向。

**修复方向。** 在 `cmd_archive` 里，剥掉 `-ed` 得到 `base` 之后、去原图目录匹配之前，加一道扩展名闸门：**成品的扩展名必须在图片扩展名白名单里**（可以直接复用 `JPG_EXT`，必要时并上 `RAW_EXT` 里的 `.dng` 等可预览格式）。不在白名单的，归入 `orphan`（「成品目录里不是成品的文件」），既不触发归档、也不计入「已修」。这一处改动同时能让 `doctor` 的判定和 `archive` 保持一致。

### P1-1　`-ed.jpg` 成品普遍无法归档 `.HEIC` 原图，照片在时间线里重复

**现象。** `archive` 匹配原图的顺序是：先按「主名 + 扩展名」精确匹配；只有精确匹配落空、且原图目录里**恰好只有一个**候选时，才允许跨扩展名匹配。实测三种典型组合的结局：

| 原图目录里有什么 | 成品 | 结果 |
|---|---|---|
| 只有 `DSC0001.HEIC` | `DSC0001-ed.jpg` | ✅ 归档 HEIC（单候选跨扩展名） |
| `DSC0001.HEIC` + `DSC0001.JPG` | `DSC0001-ed.jpg` | ⚠️ **只归档 JPG，HEIC 留在原图目录** |
| `DSC0001.HEIC` + `DSC0001.PNG` | `DSC0001-ed.jpg` | ⚠️ **报「匹配不唯一」，两张都不动** |

后两种才是最贴近手机拍的组合（相机常常同时写 HEIC 和 JPG，或相册里一边是 HEIC 一边是 PNG 截图）。被留下的 HEIC 原图仍在被索引的原图目录里，而 JPG 成品进了被索引的成品目录——**同一张照片在时间线里出现两次**，恰好违背工具「每张照片只出现一次」的核心目标。

**复现（临时目录实测，已确认）：**

```
C) 05 有 DSC0001.HEIC + DSC0001.JPG，03 有 DSC0001-ed.jpg
   $ photoflow archive ... --apply
   待归档 1 个
   完成：归档 1 个 ...            ← 只归档了 .JPG
   归档后 05 里还剩：DSC0001.HEIC ← 会被相册索引，和成品重复
   $ photoflow doctor
   INFO ...：1 张（同名的 HEIC / TIF 之类还在原图目录里，脚本不自动搬）

N) 05 有 DSC0001.HEIC + DSC0001.PNG，03 有 DSC0001-ed.jpg
   $ photoflow archive ...
   待归档 0 个
    WARN 匹配不唯一 1 个 —— 不自动移动，需你人工确认：
          DSC0001-ed.jpg：扩展名不一致，且有多个同名候选
              候选 .../DSC0001.HEIC
              候选 .../DSC0001.PNG
```

工作流说明文档把「HEIC 原图 + JPG 成品就手动挪进归档目录」写成了需人工处理的步骤。问题在于，这恰恰是**手机照片最常见的形态**，而「手动逐张判断、逐张挪」正是这套工具声称要消灭的机械劳动。文档承认了它，但没解决它。

**修复方向。** 先把「扩展名」从「能否匹配的门槛」降级为「候选的排序权重」：剥掉 `-ed` 得到 `base` 后按主名取全部候选，正好一个就直接用；多个时优先取与成品扩展名相同（大小写不敏感）的那个。这一改至少能让「`HEIC + JPG` + `-ed.jpg`」这种最常见的组合自动归档正确的 JPG，不再每张报歧义。

但要说清楚：**这是文件名匹配的固有局限，不能靠「自动把同主名的其它格式一并归档」来草率解决。** 因为 `test_02` 已经确认过「同主名不同内容 = 两张不同照片」是真实存在的场景，脚本无法从文件名判断「HEIC + JPG」到底是同一张的两个格式、还是两张碰巧同名的不同照片。盲目一起归档有退掉真实照片的风险，也违背工具「匹配不唯一就不动手」的保守哲学。所以更好的做法是：把这类「同主名多格式」的场景收拢成**一条可批量确认的动作**——在预演里列出「这批里有 N 张存在 HEIC/JPG 同主名，是否把它们当作同一张、一并归档？」让用户一次性确认，而不是逐张手工挪。把机械劳动的「逐张判断」换成「一次确认」，既解决重复，又不牺牲安全边界。

再加上 P1-1 表格里的第一种情况（单候选跨扩展名）现在已经能自动过，大部分 HEIC-only 或 JPG-only 的手机批次无需人工介入，只有 HEIC+JPG 双格式并存时才需要确认。

### P1-2　`doctor` 对 JPG-only 批次误报「缺 RAW 目录」

**现象。** `doctor` 的「批次目录不齐」检查把 RAW 和原图两个目录都当成「必须有」。但工作流里明确存在「只有 JPG、没有 RAW」的批次——手机随手拍、视频截图、从别处拷来的老照片。这些批次每次体检都会被报 `WARN ... 缺 RAW 目录`，属于持续的噪音，时间一长会让人对 `WARN` 脱敏，反而漏掉真正的漏归档告警。

**复现（临时目录实测，已确认）：**

```
05_JPG图/比特/IMG_1.jpg
05_JPG图/2026-11-20-手机随手拍/IMG_2.jpg
（两个批次都没有 04_RAW原图 对应目录）

$ photoflow doctor
 WARN 2026-11-20-手机随手拍：有 原图目录，缺 RAW 目录
 WARN 比特：有 原图目录，缺 RAW 目录
```

而工作流说明文档自己列出的真实例外里就有「`比特`：没有日期」，说明这类批次是预期内的存在。

**修复方向。** 「缺 RAW 目录」从 `WARN` 降为 `INFO`，或者只在该批次的**其他目录也不齐**时才升级为 `WARN`（即：如果原图目录存在、成品目录也存在、唯独 RAW 缺失，大概率是手机批次，不该警告；如果四个目录都零散存在，才提示可能是目录建漏了）。至少要让「缺 RAW」不抢「漏归档」的风头。

### P2-1　文档声称的默认根目录与代码里的常量不一致

- 工作流说明第六节：「`--root PATH` 指定照片库根目录，**默认写死 J 盘路径**」
- `photoflow.py` 第 50 行：`DEFAULT_ROOT = r"E:\TMP\outputs"`

文档描述的是真实照片库（`J:\sata11-...`），代码默认值是一个临时目录。两者不一致的后果是：用户不传 `--root`、配置里也没存根目录时，所有命令会悄悄指向 `E:\TMP\outputs`——而这个目录往往不存在或内容是空的，`new --apply` 会在那里凭空造出四个目录（见下一条 P2-2）。

**修复方向。** 要么把 `DEFAULT_ROOT` 改成真实路径（但那样等于把个人路径写进代码，不适合开源），要么在文档里如实写明「默认值仅为占位，正式使用必须用配置文件或 `--root` 指定」，并在缺少有效根目录时直接报错而不是造目录。

### P2-2　`new` 不校验根目录是否存在，路径打错时会在错误位置默默造目录

**现象。** `new` 是唯一不调用 `check_root` 的命令。它不是在建好的照片库里按批次名建四个子目录，而是**从根目录开始按需创建整条路径**。根目录路径打错一个字母（或盘符没挂载、临时目录默认值生效），它不会报错，而是照常在错误位置造出 `04_RAW原图/03_缓存-调色ed/...` 四个目录，报「新建 4 个」。

**复现（临时目录实测，已确认）：**

```
$ photoflow new 2026-11-26-测试 --root /tmp/probe/typo_root_NOT_EXIST --apply
  OK  RAW  新建    .../typo_root_NOT_EXIST/04_RAW原图/2026-11-26-测试
  OK  JPG  新建    .../typo_root_NOT_EXIST/05_JPG图/2026-11-26-测试
  OK  成品 新建    ...
  OK  归档 新建    ...
新建 4 个，已存在 0 个。
```

**修复方向。** `new` 在真正建目录前，先确认**根目录本身存在**（`root` 是目录）。根目录不存在就报错并提示「照片库根目录不存在，检查盘符是否挂载 / 路径是否打错」。四个业务目录可以在根目录下按需创建，但根目录不能凭空造。这条改动和 `check_root` 现有的「找不到 RAW 目录就 die」一脉相承，只是把闸门前移到根目录层。

### P2-3　测试在当前目录结构下跑不起来

**现象。** 两个测试脚本的路径假设都和多文件布局对不上：

- `test/test_photoflow.py` 第 25 行 `SCRIPT = HERE / "photoflow.py"`，`HERE` 是 `test/` 目录，但主程序在上一级，于是每个用例都报 `can't open file '.../test/photoflow.py'`。实测 24 个用例里 16 失败、7 报错。
- `test/verify_fixes.py` 第 23 行 `import photoflow as pf`，同样找不到主程序，直接 `ModuleNotFoundError`。

把主程序软链进 `test/` 之后，`test_photoflow.py` 24 个用例全绿，`verify_fixes.py` 三项加固全部通过——**说明代码本身没问题，是测试的路径没跟上「测试挪进 test/ 子目录」这次重构**。

**修复方向。** `test_photoflow.py` 改成 `SCRIPT = HERE.parent / "photoflow.py"`；`verify_fixes.py` 把 `sys.path.insert(0, str(HERE.parent))` 而不是 `str(HERE)`。文档里「跑测试：`python test_photoflow.py`」也应同步为 `python test/test_photoflow.py`（或补一句在 `test/` 下跑）。

### P2-4　文档和代码的其它几处小出入（不影响正确性，但会误导维护）

- README 两份都写「`test_photoflow.py` 回归测试，**18 个用例**」，实际是 **24** 个。
- `photoflow.bat` 工作区里有一处未提交改动，但 `diff` 下来只是换行符 CRLF↔LF 的差异，没有实质改动。建议 `git checkout` 掉，并加一个 `.gitattributes`（`*.bat text eol=crlf`）统一换行符，避免以后 Windows 上反复出现整文件 diff。

## 三、优化建议（按性价比排序，非缺陷）

1. **`-ed` 命名多一种分隔符支持。** 现在只认 `-ed` / `-ed2` / `-ed-2` / `-ed-Edit`，不认 `_ed`。如果用户某个导出预设用了下划线，会被当成「不带 -ed 的文件」漏掉。加一条 `_ed` 的正则是低风险改动。

2. **`archive` 的「匹配不唯一」提示可以更可操作。** 现在只列候选就停手。可以加一个 `--pick <扩展名>` 之类的交互或参数，让用户在确认「这批 HEIC 都要归档」时能一把过，而不是每张都手动挪。考虑到照片库是 NAS、批量场景多，这个能省不少手工。

3. **重复分发的哈希成本可以加一个「修改时间」快路径。** 压测报告第七节已经分析过：同一张卡重跑 ingest，10GB 要 280 秒，全是两头各算一遍 SHA-256。报告里建议的 `--quick`（同大小且同修改时间就跳过哈希）方向是对的，因为 `copy2` 保留了 mtime。这个开关做成 opt-in 就不会动到「内容判定看哈希」这条安全底线。

4. **`ingest` 的 `--verify` 默认关、但可以给一个「首次导入默认开」的策略。** 读卡器掉线导致「大小对、内容错」是真实存在的故障模式，而 `ingest` 默认只比大小。对不可重建的相机素材，首次导入默认 `--verify` 更稳妥；重复分发时再关掉省时间。

5. **`-ed` 伴生文件的清理可以做成 `doctor` 的一个可选动作。** 一旦 P0-1 把非图片文件挡在归档之外，这些文件会一直留在成品目录（因为不触发归档、也没有地方去）。可以在 `doctor` 里单独列出来并给一条 `--clean-sidecars` 之类的清理入口，而不是让它们静默堆积。

## 四、没问题的部分（供对照，避免过度修改）

这几处实测下来是稳的，后续改动不要动到它们：

- **跨卷归档的原子性**：`move_verified` 在 `os.rename` 抛 `EXDEV`/`winerror 17` 时才退化成「复制 + 哈希校验 + 删源」，校验失败时原图保留、归档目录不落错文件（`verify_fixes.py` 第 2 项通过）。
- **预演指纹锁清单**：预演后目录里多了文件，带旧指纹执行会被拒绝，重新预演拿到新指纹才放行（`test_photoflow.py` `test_24` 通过）。
- **批次名路径校验不依赖 `Path.resolve()`**：极空间这类网络卷上 `resolve()` 会抛 `WinError 1005`，代码用纯字符串 `normpath + commonpath` 绕开了（`test_12`、`test_13` 通过）。
- **复制中途失败不留半截文件**：`copy_verified` 先写 `.phototmp` 临时文件，校验通过才 `os.replace`，Ctrl-C 也会清理（`test_21` 通过）。
- **同名文件先比大小、再比 SHA-256**：`same_content` 的短路顺序正确，且刻意不做跨调用哈希缓存，避免文件被改写后误判（`test_09` 通过）。

## 五、修复优先级建议

| 优先级 | 问题 | 改动位置 | 改动量 |
|---|---|---|---|
| **P0** | 非图片 `-ed` 文件触发归档 | `cmd_archive` 匹配前加扩展名白名单 | 小 |
| **P1** | 扩展名门槛过严导致 HEIC 等漏归档 / 时间线重复 | `cmd_archive` 扩展名改排序 + 多格式汇总确认 | 中 |
| **P1** | `doctor` 误报 JPG-only 批次缺 RAW | `cmd_doctor` 的目录不齐检查 | 小 |
| **P2** | `DEFAULT_ROOT` 与文档不一致 | 代码常量或文档 | 小 |
| **P2** | `new` 不校验根目录 | `cmd_new` 开头加根目录检查 | 小 |
| **P2** | 测试路径假设错误 | `test_photoflow.py` / `verify_fixes.py` 路径常量 | 小 |
| **P2** | 文档用例数、换行符 | README / `.gitattributes` | 小 |

P0 建议在下次用这台机器归档前就修掉——它是唯一一条能让照片「看起来修了但时间线里没了」的路径，而且触发条件（伴生文件混进成品目录）在日常使用里不算罕见。
