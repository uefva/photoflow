# photoflow 压力测试报告

测试日期：2026-12-20
被测版本：`python/photoflow.py`（含图形界面、可配置目录、单一批次选择器）
被测命令：`new` / `ingest` / `archive` / `doctor`

---

## 一、测试目的

回答三个问题：

1. 数据量上去之后，内存会不会跟着涨（有没有把大文件整个读进内存）。
2. 每一步的耗时随数据量怎么变，瓶颈在哪。
3. 万级文件、10GB 规模下，结果是否仍然正确（不丢片、不串目录、统计准确）。

## 二、测试环境

| 环境 | 说明 |
|---|---|
| A. 本机（Windows） | 源和目标都在 `D:\stress`，**同一块本地盘**，单盘同时读写 |
| B. 沙箱（Linux） | 源和目标在同一 overlay 文件系统，用于对照与小文件海量测试 |
| C. 沙箱（稀疏） | 10GB 逻辑数据 / 2 万文件，用稀疏文件 + 硬链接占位，**只测扫描不测真实写入** |

两点必须说明的影响因素：

- **单盘读写互相抢磁头**。环境 A 里「造卡」和「分发」是同一块盘一边读一边写，机械盘吞吐会掉到顺序读写的 50%～60%，SMR 盘还会更低。所以 A 的拷贝速度不代表真实工作流（真实是卡走 USB、库走 NAS）。
- **Windows 没有内存采样**。报告里环境 A 的内存列是空的；内存结论来自环境 B 的 `/proc/<pid>/status` 峰值读取。

## 三、测试方法

`python/stress_test.py` 依次执行：

1. **造卡**：按目标总量和文件数生成假照片，一半 `.CR3`、一半 `.JPG`，大小带 ±20% 抖动，分放在两个子目录（模拟相机的 `100CANON` / `101CANON`）。
2. **建批次**：`new --apply`。
3. **首次分发**：`ingest --apply`，真实拷贝。
4. **重复分发**：同一张卡再跑一次，此时所有文件同名同大小，逐个走 SHA-256 比对。
5. **模拟修图**：给 20% 的 JPG 造 `-ed` 成品（200KB 小文件，不参与数据量统计）。
6. **归档**：`archive --apply`。
7. **体检**：`doctor`。

每一步都记录墙钟时间、退出码、子进程峰值内存（Linux 下轮询 `VmHWM`）。
正确性判据：分发后 RAW + 原图目录的**字节数必须等于卡上总量**；归档的**文件数必须等于成品数**。

## 四、结果数据

### 4.1 环境 A：10GB / 200 个文件（本机单盘，真实读写）

| 步骤 | 耗时 | 折算吞吐 | 备注 |
|---|---:|---:|---|
| 造卡（仅写入） | 112.6 s | 95 MB/s | 纯写，作为该盘的上限参考 |
| new | 3.66 s | — | 4 次 mkdir 排在 10GB 刷盘队列后面 |
| ingest 首次 | 188.8 s | 56.7 MB/s | 同盘读+写，磁头交替 |
| ingest 重复 | 280.3 s | — | 读卡 10GB + 读库 10GB = 20GB |
| archive | 0.60 s | — | 移动 20 个文件（1.0GB），同卷改名 |
| doctor | 0.11 s | — | 扫描 200 个文件 |

正确性：RAW 5.0GB + 原图 5.0GB = 卡上 10.0GB，逐字节对上；归档 20 个 = 成品 20 个。

### 4.2 环境 B：3.5GB / 70 个文件（大文件，真实读写）

|---|---:|---:|---:|
| new | 0.10 s | — | 18 MB |
| ingest 首次 | 34.9 s | 108 MB/s | 18 MB |
| ingest 重复 | 21.0 s | — | 20 MB |
| archive | 0.06 s | — | 18 MB |

### 4.3 环境 B：2.0GB / 12000 个文件（小文件海量，真实读写）

| 步骤 | 耗时 | 折算吞吐 | 峰值内存 |
|---|---:|---:|---:|
| new | 0.08 s | — | 18 MB |

### 4.4 环境 C：10GB / 20000 个文件（稀疏，只测扫描）

| 步骤 | 耗时 | 峰值内存 |

| new | 0.08 s | 18 MB |

| doctor（扫描 2 万条） | 0.16 s | 23 MB |

## 五、分析

### 5.1 内存：与数据量无关

从 200 张到 2 万张、从 2GB 到 10GB，峰值内存始终在 **18～52MB** 之间，只随「文件条数」轻微上升，不随「单文件大小」上升。说明实现是逐文件流式处理：读一块、写一块、比对大小，从不把整个文件读进内存。这一项可以放心，再大的单文件也不会把机器拖死。

### 5.2 首次分发：纯粹是磁盘/网络带宽

- 本机单盘：56.7 MB/s（读+写同一块盘，磁头来回跑）
- 沙箱：107～122 MB/s

脚本在拷贝路径上没有额外计算——`ingest` 对每个文件只做「复制 → 比对大小」，不碰哈希。所以这一步的耗时就是你硬件的物理上限，换成卡走 USB、库走 NAS，速度由两者中较慢的一个决定。

### 5.3 重复分发：唯一的算法级开销，也是最值得关注的一项

10GB 重跑一次要 **280 秒**，比首次分发还慢 48%。原因很直接：每个同名同大小的文件都要**两头各算一遍 SHA-256**，也就是读 10GB 卡 + 读 10GB 库 = 20GB 的读。单盘上两组文件交替读，磁头来回寻道，合起来只有约 76 MB/s。

这是 2026-11-26 明确要求的正确性设计（「大小相同也必须比哈希，不能只看大小」），不是 bug。但它带来一个实际问题：**同一张卡第二次 ingest，成本约等于把这张卡重读两遍**。

### 5.4 归档：与数据量无关，只与移动的文件数有关

10GB 规模下归档 20 个文件只用 0.60 秒，2GB 规模下归档 1200 个文件 0.22 秒。因为同卷内移动是改名（rename），不搬运数据。真正慢的情况只有一种：原图和归档目录不在同一个卷上，那时会退化成复制。

### 5.5 体检：线性扫描，极快

2 万条文件 0.16 秒，约 10 微秒/文件。日常几十个批次、几千张照片，体检基本是瞬时的。

## 六、结论

1. **没有正确性问题**。所有规模下退出码为 0，字节数与文件数逐项对上，归档数量与成品数量一致。
2. **内存不随数据量增长**，峰值 52MB 封顶，可以放心处理超大单文件。
3. **首次分发 = 硬件速度**，脚本没有额外损耗。
4. **重复分发 = 哈希成本**，10GB 约 280 秒（单盘）。这是唯一值得优化的点。
5. **归档与体检的开销可以忽略**，即使在 10GB / 2 万文件规模下也是零点几秒。

## 七、建议

**如果「同一张卡重跑 ingest」是常见操作**，可以增加一个可选开关：

```
photoflow ingest <卡> <批次> --quick --apply
```

规则是「大小相同 **且** 修改时间相同 → 视为同一张，跳过哈希」。因为文件是用 `copy2` 拷的，修改时间会被原样保留，所以重跑同一张卡时几乎全部命中，280 秒可以降到十几秒。

代价是：如果某个文件被改过内容、但被人为保留了修改时间、且大小恰好没变，会被误判成重复。这是极端情况，默认不开，需要时显式加参数。

**要拿到真实工作流的数字**，还需要一次分设备测量：卡在一个盘、照片库在 NAS，源和目标不能同盘。现有脚本只有一个 `--workdir`，可以加 `--card-dir` 把源指到另一块盘。

## 八、复现方式

```bash
# 10GB / 200 个大文件（需要约 20GB 空闲空间）
python python/stress_test.py --workdir D:\stress --size-gb 10 --files 200

# 10GB / 2 万个小文件
python python/stress_test.py --workdir D:\stress --size-gb 10 --files 20000

# 只测扫描、不真实写入（几乎不占空间）
python python/stress_test.py --workdir D:\stress --size-gb 10 --files 20000 --sparse

# 保留现场排查
python python/stress_test.py --workdir D:\stress --size-gb 10 --files 200 --keep
```

脚本默认跑完删除临时数据；中途 Ctrl-C 不会触发清理，需手动删除 workdir。
